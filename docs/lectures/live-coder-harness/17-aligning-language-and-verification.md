# 第17回 言葉をそろえ、先に確認方法を置く

副題: DDD と TDD をやさしく締めくくる

## この回の位置づけ

第16回では、Clean Architecture を「置き場所のルール」として整理し、役割を混ぜない設計を見ました。

第17回では、この講義全体の最後として、`DDD` と `TDD` をやさしく整理します。

この回の主役は `DDD` と `TDD` ですが、専門理論を詳しく学ぶ回ではありません。
ここまで見てきた流れを、「言葉をそろえる」「先に確認方法を置く」という2つの習慣でまとめる回です。

## 対象

- エンジニアではないライブコーダー
- DDD や TDD という言葉を聞くと難しく感じる人
- 講義全体を設計の視点で一度まとめたい人

## この回のゴール

- DDD を「言葉をそろえる考え方」として説明できる
- TDD を「先に確認方法を置く考え方」として説明できる
- glossary や contract card の意味を説明できる
- test を後回しにしない理由を説明できる

## この回で伝えたい中心メッセージ

- 設計は難しい図を描くことだけではありません
- まず大事なのは、同じ言葉で話せることです
- そして、何をもって「できた」と言うかを先に置くことです
- DDD と TDD は、どちらも作業を安定させるための習慣として見ると分かりやすいです

## 導入で使う一言

> 難しい設計用語も、実は「言葉をそろえる」「確認方法を先に決める」と言い換えるとかなり身近になります。  
> 今日は、その視点で DDD と TDD を最後に整理します。

6. 全17回の締め

## 1. DDD をやさしく言うと何か

### やさしい説明

- アプリの中で大事な言葉をそろえる考え方
- 画面の言い方、会話の言い方、コードの名前がずれすぎないようにする

### この回での言い方

- 言葉をそろえる設計
- アプリの中の名前をぶらさない考え方

### ここで伝えること

- UI の言い回しは変わりやすい
- でも、中心に置く言葉はあまりぶれない方がよい
- その違いを意識するだけでも、かなり整理される

## 2. 言葉をそろえると何が楽になるのか

### この環境で見えるもの

- glossary
- contract card
- `define-domain-language`

### glossary をやさしく言うと

- 大事な用語の辞書
- 同じ言葉を、同じ意味で使うための表

### この環境での見方

- `L1`: 変えにくい中心の言葉
- `L2`: UI で見せる言い方や場面に応じた言い方

### ここで伝えること

- UI ラベルをそのまま内部の型名にしない
- 変えやすい言葉と、固定したい言葉を分ける
- そうすると、UI の文言変更で中心ルールまで揺れにくくなる

### 講師が言える一言

- 「見せる言葉」と「中で支える言葉」を分けるだけで、かなりぶれにくくなります

## 3. TDD をやさしく言うと何か

### やさしい説明

- 実装する前に、何をもって正しいと言うかを先に置く考え方
- つまり、確認方法を先に決めてから作る

### この回での言い方

- 先に確認方法を置く進め方
- できたかどうかの基準を先に置く考え方

### ここで伝えること

- 作ってから「どう確認しよう」と考えると、基準がぶれやすい
- 先に確認方法を置くと、何を作るべきかがはっきりしやすい

## 4. 先に確認方法を置くと何が楽になるのか

### この環境でつながるもの

- Storybook
- test
- review
- checklist

### ここで伝えること

- UI なら Storybook で状態を先に考える
- domain / application なら test を先に考える
- verify や review まで含めて、どこで確認するかを先に置く

### checklist とのつながり

- invariant を実装前に列挙する
- domain / use case の変更なら test を先に書く
- story / test / implementation を揃える

### 講師が言える一言

- TDD はテストを書く作法というより、確認の基準を先に置く習慣として見ると分かりやすいです

## 5. この環境ではどう実践しているか

### DDD 側で見えるもの

- `docs/process/domain-glossary.md`
- `define-domain-language`
- contract card 更新

### TDD 側で見えるもの

- `test`
- Storybook-first
- `verify:all`
- harness implementation checklist

### ここで伝えること

- この環境では DDD も TDD も、理論だけでなく docs と command に落ちている
- つまり、「知っている」だけでなく、「その場で使える」ようにしている

## 6. 全17回の締め

### ここまでの流れを一言でまとめる

- 最初は環境を知る
- 次に動かし、確認し、追えるようにする
- その上で、AI・review・quality・parallel・provider を整える
- 最後に、言葉と確認方法をそろえる設計へ戻る

### この講義全体で残したいこと

- ハーネスエンジニアリングは、難しい仕組みを増やすことではない
- 安全に繰り返せる作業場を作ること
- そのために、言葉、確認、入口、出口、review、運用をそろえていくこと
