# 第5回 見えないミスを早めに止める

副題: ESLint、Prettier、Typecheck は何を守っているのか

## この回の位置づけ

第4回では、Storybook を使って画面の部品を 1 つずつ見る方法を学びました。

第5回では、見た目では気づきにくいミスを早めに止めるための道具を扱います。

この回の主役は `ESLint`、`Prettier`、`Typecheck` ですが、難しい定義を覚えることが目的ではありません。
それぞれが何を防いでいるのかを、ライブコーダーにも分かる言葉でつかむことが目的です。

## 対象

- エンジニアではないライブコーダー
- エラーや警告が出ても、何の種類の問題かまだ分かりにくい人
- 「動けばよい」だけでは不安が残ると感じている人

## この回のゴール

- `Prettier`、`ESLint`、`Typecheck` の役割をざっくり説明できる
- 見た目の確認と、書き方や受け渡しの確認は別だと理解する
- どのコマンドがどの種類のミスを見ているか分かる
- 警告やエラーが出た時に、まず何を確認するか判断しやすくなる

## この回で伝えたい中心メッセージ

- こうしたチェックは、作業を邪魔するためではなく、事故を早めに止めるためにあります
- アプリが「たまたま動く」ことと、「安心して直せる」ことは別です
- Storybook が見た目の確認場所だとすると、今回の道具は見えない崩れを見つけるための見張り役です

## 1. なぜ見えないチェックが必要なのか

### 伝えること

- 画面が表示されても、中に危ない書き方や受け渡しミスが残っていることがある
- そのまま進むと、あとで大きな崩れ方をする
- だから、早い段階で止めてくれる仕組みが必要になる

### 話す例

- 見た目はきれいでも、ネジがゆるんでいたら不安です
- UI も同じで、動いて見えても内側の危険は別にあります

## 2. Prettier は何をするのか

### やさしい説明

- 書き方の見た目をそろえる道具
- インデントや改行のばらつきを減らす
- 読む人によって見え方が変わりにくくなる

### この回での言い方

- 見た目をそろえる係
- 書き方の整頓係

### 実演コマンド

```bash
npm run format:check
```

### ここで伝えること

- Prettier は「正しい機能」を保証する道具ではない
- でも、読みやすさとチームのそろい方を守る

## 3. ESLint は何をするのか

### やさしい説明

- 危ない書き方や、チームで避けたい書き方を見つける道具
- ただの見た目ではなく、書き方のルールを見る

### この回での言い方

- 書き方の危険予知
- うっかりミスの見張り役

### 実演コマンド

```bash
npm run lint
```

### ここで伝えること

- ESLint は「こう書くと後で困りやすい」を止める
- すぐ壊れないコードでも、将来困る形を早めに止めることがある

## 4. Typecheck は何をするのか

### やさしい説明

- データの受け渡しが合っているかを見る道具
- 期待している形と、実際に渡している形がずれていないかを確認する

### この回での言い方

- 受け渡しミス検知
- データの約束違反を見つける係

### 実演コマンド

```bash
npm run typecheck
```

### ここで伝えること

- 文字だと思っていたのに数字が来る
- 必要な項目が足りない
- 受け取る側と渡す側で前提が違う

こうしたズレを早めに見つけるのが Typecheck です。

## 5. 3つをどう使い分けるか

### シンプルな整理

- Prettier: 見た目をそろえる
- ESLint: 書き方の危険を止める
- Typecheck: 受け渡しのズレを止める

### Storybook との違い

- Storybook: 見た目や状態を見る
- Prettier / ESLint / Typecheck: コードの内側を見る

### 講師が言える一言

- Storybook は外から見る確認
- 今回の 3 つは中の崩れを早めに見つける確認
