# 第9回 request と response の約束をそろえる

副題: API の入口と出口を、ぶれない形にする

## この回の位置づけ

第8回では、ログと `requestId` を使って、問題が起きた時に何を手がかりに追えばよいかを整理しました。

第9回では、その一歩手前に戻って、「そもそも入口と出口の約束をそろえておく」考え方を扱います。

この回の主役は `request`、`response`、`code`、`requestId` ですが、API 設計の専門理論を学ぶ回ではありません。
受け取るものと返すものを毎回似た形にそろえると、なぜ楽になるのかをつかむ回です。

## 対象

- エンジニアではないライブコーダー
- API という言葉は聞くが、まだ感覚的にしか分からない人
- 失敗した時の返り方が毎回違うとつらいと感じている人

## この回のゴール

- `request` と `response` を「受け取るもの」「返すもの」として説明できる
- 入口と出口の約束をそろえる意味を説明できる
- エラー時に `code` と `requestId` があると何が助かるか分かる
- 「自由に返すより、そろえて返す方が楽」という感覚を持てる

## この回で伝えたい中心メッセージ

- API は、ただデータをやり取りするだけでなく、約束を守ってやり取りする仕組みです
- 入口が毎回ばらばらだと受け取る側が困る
- 出口が毎回ばらばらだと、使う側も追う側も困る
- だから、受け取る前に確かめ、返す前にも確かめることが大事です

## 導入で使う一言

> 同じ窓口なのに、日によって受け付け方法も返事の形も違ったら困ります。  
> 今日は、API の入口と出口をそろえる考え方をやさしく整理します。

5. この環境でどうそろえているか
6. 次回へのつながり

## 1. API をやさしく言うと何か

### 伝えること

- API は、画面と裏側、または仕組み同士がやり取りするための窓口
- 何を受け取り、何を返すかが決まっていると使いやすい
- 決まっていないと、毎回「今回はどう返るのか」を探る必要が出る

### この回での言い方

- 受け渡しの窓口
- やり取りの約束

### 話す例

- 注文票の書き方が決まっていると、店側も受け取りやすいです
- API も同じで、やり取りの形が決まっている方が楽です

## 2. request は何の約束か

### やさしい説明

- request は、相手に渡す内容
- 何を送りたいのか、どんな形で送るのかを決める
- 受け取る前に「形が合っているか」を確認すると崩れにくい

### この回での言い方

- 入口の約束
- 受け付ける形の確認

### ここで伝えること

- JSON が壊れていないか
- 必要な項目が入っているか
- 想定外の形になっていないか

### 講師が言える一言

- 受け取ってから困るより、入口で止めた方が楽です
- 最初に形を確かめると、その後の話がかなり安定します

## 3. response は何の約束か

### やさしい説明

- response は、相手に返す内容
- 成功した時も、失敗した時も、ある程度そろった形で返した方が使いやすい
- 返す前に「返し方が約束どおりか」を見ると安心しやすい

### この回での言い方

- 出口の約束
- 返し方の整え方

### ここで伝えること

- 成功時は成功時の形がある
- 失敗時は失敗時の形がある
- 出口が毎回違うと、画面側もログ側も追いにくくなる

## 4. エラーの返し方をそろえると何が楽か

### この環境で大事にしているもの

- `code`
- `requestId`

### `code` をやさしく言うと

- 何の種類の失敗かを短く表す印
- 人の文章だけより、機械や人が判断しやすい

### `requestId` をやさしく言うと

- どの出来事の失敗かをたどるための目印
- ログと画面をつなぎやすくする

### ここで伝えること

- 失敗メッセージだけだと、表現が毎回ぶれやすい
- `code` があると種類で整理しやすい
- `requestId` があると、どの記録を見ればよいか分かりやすい

### 話す例

- 「壊れました」だけより、「どの種類で、どの出来事か」が分かる方が助かります

## 5. この環境でどうそろえているか

### この環境の基本パターン

- request を読む前に確かめる
- response を返す前に確かめる
- 想定される失敗は、安定した `code` と `status` に写す
- 想定外の失敗は、細かい内部事情を表に出しすぎない

### この回で紹介する名前

- `readRequestJson`
- `jsonResponse`
- `errorResponse`
- `handleRouteError`

### ここでの伝え方

- request を読むための入口
- 成功を返すための出口
- 失敗を返すための出口
- 予想外の失敗をまとめて受ける出口

### 補助的に見せられるコマンド

```bash
npm run boundary:check
```

### ここで伝えること

- この環境では、こうした「境界のそろえ方」をルールだけでなく確認コマンドでも守っている
- つまり、気合いではなく仕組みでそろえようとしている

## 実演時に講師が言える一言

- 入口と出口の形がそろうと、作る側も使う側も迷いにくいです
- エラーの返し方が毎回違うと、画面もログも追いにくくなります
- ルールを決めるだけでなく、確認コマンドがあるのも大事です

## 受講者にやってもらう最小課題

- `request` を「受け取るもの」と一言で説明する
- `response` を「返すもの」と一言で説明する

- API は受け渡しの窓口
- 入口と出口の形がそろっていると、かなり扱いやすい
- エラー時の `code` と `requestId` は、使う側にも追う側にも役立つ
- 次回は、失敗をどう分けて返すかに進む
