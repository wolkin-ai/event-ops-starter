# 第7回 ローカルで同じデータ状態を再現する

副題: PostgreSQL、seed、db:prepare は何のためにあるのか

## この回の位置づけ

第6回では、`Vitest`、`Playwright`、`verify:all` を使って、動かして確かめるチェックを整理しました。

第7回では、その確認の土台になっている「データを毎回同じように用意する仕組み」を扱います。

この回の主役は `PostgreSQL`、`db:prepare`、`db:seed`、`db:reset-local` ですが、データベース理論を学ぶ回ではありません。
同じ状態から始められることが、なぜライブコーディングや学習で重要なのかをつかむ回です。

## 対象

- エンジニアではないライブコーダー
- 画面は起動できるが、データの準備がまだ曖昧な人
- 毎回違う表示になる理由を整理したい人

## この回のゴール

- ローカルDBが何のためにあるかを説明できる
- `db:up`、`db:prepare`、`db:seed`、`db:reset-local` の違いをざっくり説明できる
- seed が「練習用の初期データ」だと理解する
- 毎回同じ状態から始めることの価値を理解する

## この回で伝えたい中心メッセージ

- データが毎回バラバラだと、学びも確認も不安定になります
- 同じ状態を再現できると、変えたことの影響が追いやすくなります
- ローカルDBと seed は、練習しやすい土台を整えるための仕組みです

## 導入で使う一言

> 同じコードでも、データが違うと見え方や動き方が変わります。  
> 今日は、毎回なるべく同じ状態から始めるための仕組みを整理します。

## 1. なぜデータをそろえる必要があるのか

### 伝えること

- 画面はデータによって見え方が変わる
- データが毎回違うと、何が原因で変わったのか分かりにくい
- だから、学習や確認では「同じスタート地点」を作ることが大切になる

### 話す例

- 同じレシピでも材料が毎回違うと、味の比較がしにくいです
- アプリも同じで、データがそろっている方が違いを追いやすいです

## 2. ローカルDBは何をしているのか

### やさしい説明

- アプリが使う情報を、手元の環境に保存しておく場所
- このスターターでは PostgreSQL を使っている
- 公開画面や管理画面に出てくる内容の土台になる

### この回での言い方

- データの置き場
- アプリの記録場所

### 実演コマンド

```bash
npm run db:up
```

### ここで伝えること

- `db:up` は、ローカルの PostgreSQL を立ち上げる入口
- 画面の見た目そのものではなく、その裏にある情報を置くための準備

## 3. seed は何をしているのか

### やさしい説明

- 練習用の初期データを入れる仕組み
- 何もない空の状態から、最初に見られるデータを作る

### この回での言い方

- 最初に入れておく見本データ
- 練習用の初期セット

### 実演コマンド

```bash
npm run db:seed
```

### ここで伝えること

- seed があると、起動直後から確認しやすい
- 空の画面ばかりだと、何を見ればよいか分かりにくい
- サンプルイベントや公開情報が最初から入っていると、練習しやすい

## 4. `db:prepare` と `db:reset-local` の違い

### `db:prepare` のやさしい説明

- ローカルDBを使える状態に整える、安全な標準入口
- 必要な準備をまとめて進める
- 普段はこちらを使う

### 実演コマンド

```bash
npm run db:prepare
```

### `db:reset-local` のやさしい説明

- ローカルのDB状態を強くリセットする
- いつも使う入口ではない
- 状態が壊れた時や大きくずれた時にだけ明示的に使う

### 実演コマンド

```bash
npm run db:reset-local
```

### ここで伝えること

- `db:prepare` は日常用
- `db:reset-local` は例外対応用
- 強いリセットを普段の流れに混ぜないのが大事

## 5. どういう順番で使うか

### シンプルな整理

- PostgreSQL を立ち上げる: `npm run db:up`
- ローカルDBを整える: `npm run db:prepare`
- seed だけ入れ直す: `npm run db:seed`
- どうしても状態が壊れた時だけ: `npm run db:reset-local`

### 補助的に見せられる確認

```bash
npm run check:postgres -- --mode smoke
```

### ここで伝えること

- DB は触るだけでなく、確認する入口もある
- 接続できるか、必要なテーブルがあるか、見本データが入っているかを見られる

### 講師が言える一言

- 毎回全部やり直すのではなく、必要な深さで整えることが大事です
- 再現できる状態があると、画面確認もテストもかなり安定します
