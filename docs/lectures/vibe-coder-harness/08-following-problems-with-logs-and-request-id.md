# 第8回 ログと requestId で問題を追う

副題: うまくいかなかった時に、どこを手がかりにするのか

## この回の位置づけ

第7回では、ローカルDBと seed を使って、毎回似た状態から始めるための土台を整理しました。

第8回では、その次の段階として、問題が起きた時に何を頼りに追えばよいのかを扱います。

この回の主役は `ログ` と `requestId` ですが、監視システムの専門知識を学ぶ回ではありません。
崩れた時に「どこを見ればよいか」が分かるようになることが目的です。

## 対象

- エンジニアではないバイブコーダー
- エラーが出た時に、どこから見ればよいか分からなくなる人
- ログを怖いものではなく、手がかりとして使えるようになりたい人

## この回のゴール

- ログが何のためにあるかを説明できる
- `requestId` が何を助けてくれるかを説明できる
- 失敗した時に、画面だけで終わらずログを見る発想を持てる
- どの種類のログをまず見ればよいかが分かる

## この回で伝えたい中心メッセージ

- 問題が起きた時、勘で探すより、足跡をたどる方が速い
- ログは「何が起きたか」を残す記録です
- `requestId` は、たくさんの出来事の中から「今追っている1件」を見失わないための番号です

## 導入で使う一言

> うまくいかなかった時に、毎回勘で探すのはつらいです。  
> 今日は、どこを見れば手がかりが残っているのかを整理します。

## 1. なぜログが必要なのか

### 伝えること

- 画面に出るエラーだけでは、何が起きたか分からないことがある
- 裏側で何が起きたかを追うには、記録が必要になる
- ログがあると、「起きたことの順番」を追いやすくなる

### 話す例

- 現場に監視カメラがあると、何が起きたか後から追いやすいです
- ログはそれに近い役割で、アプリの中で起きたことを残しています

## 2. ログには何が残っているのか

### この環境でよく見る項目

- `timestamp`
- `level`
- `scope`
- `route`
- `method`
- `requestId`

### この回での言い方

- いつ起きたか
- どのくらい重要か
- どこで起きたか
- 何をしようとしていたか
- どの出来事か

### よく出てくるログの種類

- `request.completed`
- `request.failed`
- `request.validation.failed`
- `response.validation.failed`

### ここで伝えること

- ログは全部を読む必要はない
- まずは「失敗したのか」「どこで起きたのか」「同じ requestId はどれか」を見る

## 3. requestId は何をしているのか

### やさしい説明

- 1つのリクエストや出来事に付く番号
- 似たようなログが並んでいても、同じ流れを追いやすくする

### この回での言い方

- 出来事の整理番号
- 同じ流れを追うための目印

### ここで伝えること

- API の response header に `x-request-id` が入る
- エラーレスポンスにも `requestId` が入る
- つまり、画面側で見えた失敗と、ログ側の記録をつなげやすい

### 話す例

- 荷物の追跡番号があると、どの荷物の話かすぐ分かります
- `requestId` も同じで、今追っている1件を見失いにくくします

## 4. まず何を見ればよいか

### 最初の見方

1. 何が起きたのかを画面で確認する
2. エラーメッセージや `requestId` が見えるかを見る
3. ログの中で同じ `requestId` を探す
4. `request.failed` なのか `request.validation.failed` なのかを見る
5. route と method を見て、どこで起きたかを絞る

### ここで伝えること

- いきなりコード全体を読み始めない
- まずは「どの流れが失敗したか」を特定する
- `requestId` があると、その特定がかなり楽になる

## 5. この環境での見方

### ログを詳しく見たい時

```bash
LOG_LEVEL=debug npm run dev
```

### ここで伝えること

- 普段は `info` で十分
- 詳しく見たい時だけ `debug` にする
- いつも大量ログにしない方が見やすい

### 並列 worktree を使う時に見られるもの

```bash
./bin/worktree-harness inspect <name>
./bin/worktree-harness logs <name> app
./bin/worktree-harness observe <name> traces
./bin/worktree-harness observe <name> metrics
```

### この回での言い方

- `inspect`: どこで動いているかを見る
- `logs`: 直近の記録を見る
- `traces`: 流れの記録を見る
- `metrics`: まとめた数字を見る

### 講師が言える一言

- まずは logs で十分です
- traces や metrics は、もう少し後から使っても大丈夫です

## 実演の流れ案

1. 失敗時に画面だけでは足りないことを話す
2. `LOG_LEVEL=debug npm run dev` を見せる
3. リクエストを1回発生させる
4. ログの中の `requestId` を見る
5. `request.completed` と `request.failed` の違いを見る
6. 同じ requestId で追えることを確認する

## 実演時に講師が言える一言

- 今は全部読むのではなく、目印を見つけることが大事です
- `requestId` があると、今の失敗を他の記録と区別しやすいです
- 問題調査は、勘より手がかりの方が速いです

## 受講者にやってもらう最小課題

- `LOG_LEVEL=debug npm run dev` を実行する
- 何か1つ画面操作をする
- ログの中から `requestId` を見つける
- `request.completed` か `request.failed` のどちらかを確認する

## 受講後に残したい理解

- ログは、失敗した時の足跡
- `requestId` は、同じ出来事を追うための目印
- 画面だけで分からない時は、ログを見る発想が大事
- 次回は request / response の約束をそろえる話へ進む
