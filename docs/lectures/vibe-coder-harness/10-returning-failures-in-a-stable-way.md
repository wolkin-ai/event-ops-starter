# 第10回 失敗を安定した形で返す

副題: 4xx と 5xx、`code`、`requestId` をどう使い分けるか

## この回の位置づけ

第9回では、`request` と `response` の約束をそろえる考え方を整理しました。

第10回では、その中でも特に重要な「失敗をどう返すか」に絞って扱います。

この回の主役は `4xx`、`5xx`、`code`、`requestId` ですが、HTTP の細かい仕様を覚える回ではありません。
受け取る側が直せる失敗と、内部で調べるべき失敗を分けて返すと、なぜ扱いやすくなるのかをつかむ回です。

## 対象

- エンジニアではないバイブコーダー
- エラーが出た時に、何が「自分で直せる問題」なのか分かりにくい人
- 失敗の返し方を毎回そろえる意味を整理したい人

## この回のゴール

- 失敗を大きく 2 種類に分けて考えられる
- `4xx` と `5xx` の違いをやさしく説明できる
- `code` と `requestId` が失敗時に何を助けるか説明できる
- 失敗を感情ではなく、種類で整理する発想を持てる

## この回で伝えたい中心メッセージ

- 失敗は全部同じではありません
- 使う側が直せる失敗と、内部で調べるべき失敗は分けた方がよいです
- 返し方を毎回そろえると、画面側も調査側もかなり楽になります

## 導入で使う一言

> 「失敗しました」だけでは、その次に何をすればよいか分かりません。  
> 今日は、失敗を種類ごとに分けて返す考え方を整理します。

## セクション構成案

1. 失敗を分けて考えるとなぜ楽か
2. 4xx はどんな失敗か
3. 5xx はどんな失敗か
4. `code` と `requestId` は失敗時に何をしているか
5. この環境での返し方
6. 次回へのつながり

## 1. 失敗を分けて考えるとなぜ楽か

### 伝えること

- 失敗が起きても、毎回同じ原因とは限らない
- 入力の問題なのか、権限の問題なのか、内部の問題なのかで次の動きが変わる
- だから、失敗をひとまとめにせず、種類で分けて返す方が扱いやすい

### 話す例

- 忘れ物をしたのか、道が通れないのか、店側が閉まっていたのかでは、次の行動が違います
- アプリの失敗も同じで、種類が分かる方が次に進みやすいです

## 2. 4xx はどんな失敗か

### やさしい説明

- 相手が直せる可能性がある失敗
- 入力が足りない、形式が違う、権限が足りない、対象が見つからない、など

### この回での言い方

- 修正可能な失敗
- 使う側で直せるかもしれない失敗

### ここで伝えること

- 入力の形が違う
- ログインが必要
- 権限が足りない
- 対象が見つからない

### 講師が言える一言

- 4xx は「もう一度やり方を直せば進めるかもしれない失敗」です

## 3. 5xx はどんな失敗か

### やさしい説明

- 使う側では直しにくい、内部側の失敗
- 想定外の崩れや、裏側の問題が多い

### この回での言い方

- 内部で調べる失敗
- 使う側では直しにくい失敗

### ここで伝えること

- 詳しすぎる内部事情は、そのまま表に返しすぎない方がよい
- 代わりに、安定した `code` と `requestId` を返して、内部ではログを見る

### 講師が言える一言

- 5xx は「画面側でがんばっても直しにくい失敗」です

## 4. `code` と `requestId` は失敗時に何をしているか

### `code` の役割

- 何の種類の失敗かを短く示す
- 文章が少し変わっても、種類で整理しやすい

### `requestId` の役割

- どの出来事の失敗かを追う
- ログの中の記録とつなぎやすくする

### ここで伝えること

- 4xx にも 5xx にも `code` があると整理しやすい
- 特に調査時は `requestId` がかなり助かる
- 「何の失敗か」と「どの出来事か」を分けて持つのが大事

## 5. この環境での返し方

### この環境で大事にしていること

- 想定される失敗は、安定した `status` と `code` に写す
- 想定外の失敗は、細かい内部事情を返しすぎない
- 詳細はログに残し、表には必要な情報だけ返す

### この回で紹介する名前

- `errorResponse`
- `handleRouteError`
- `RouteContractError`

### ここでの伝え方

- 明示的に失敗を返すための出口
- 想定外の失敗をまとめて受ける出口
- 失敗の種類を持って運ぶための形

### 補助的に見せられる考え方

- expected failure
- unexpected failure

### この回での言い方

- 予想していた失敗
- 予想外の失敗

### ここで伝えること

- 「入力が違う」は予想しておけることが多い
- 「内部で崩れた」は予想外として扱うことが多い
- 両方を同じ返し方にしない方が、使う側にも調べる側にも親切
